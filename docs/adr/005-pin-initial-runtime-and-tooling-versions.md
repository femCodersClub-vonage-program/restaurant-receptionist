# ADR-005: Pin the initial runtime and tooling versions

## Status

Accepted on 2026-11-02.

## Context

The initial technical setup needs reproducible versions that work on contributor machines, Docker, CI, and the selected Spring Boot and Next.js toolchains. The project must avoid unbounded `latest` dependencies while keeping routine library versions managed by the framework dependency managers where appropriate.

## Decision

The initial setup will use the following versions and version-management approach:

| Component | Decision |
| --- | --- |
| Java | Java 21 LTS |
| Spring Boot | 4.1.2 |
| Backend build | Maven Wrapper generated by Spring Initializr |
| Node.js | Node.js 22 LTS for the supported development and CI environment |
| Frontend package manager | npm 10 |
| Next.js | 16.4.4, created with the official `create-next-app` CLI |
| PostgreSQL | Official PostgreSQL 17.11 image for Docker Compose and PostgreSQL-based tests |
| Docker Compose | Compose specification supported by Docker Compose v2 |

The backend will use Spring Boot dependency management for compatible versions of Spring Data JPA / Hibernate, Flyway, and Testcontainers. The frontend will commit its npm lockfile. Docker image tags will use the PostgreSQL patch version rather than a floating major or `latest` tag.

## Alternatives considered

- Use floating `latest` tags and dependencies. This would make local development and CI less reproducible.
- Require a globally installed Maven version. Maven Wrapper gives the project a consistent build tool version for every contributor and CI.
- Introduce pnpm, Yarn, or Bun. npm is already available to the mentor, works with the official Next.js CLI, and avoids an additional onboarding requirement for this first frontend project.
- Use the newest PostgreSQL major release. PostgreSQL 17.11 is a supported, stable release and keeps the first setup conservative while the pilot validates its core flow.

## Consequences

- `docs/setup.md` and CI must state and validate these runtimes.
- The generated Maven Wrapper and committed npm lockfile become the authoritative build inputs for application dependencies.
- Dependency upgrades are deliberate changes: they must be tested and recorded through the usual issue and pull-request workflow.
- The team should update Java 21 installations with current security patches when practical; the mentor's currently installed Java 21.0.5 does not block initial development.
